Repair must address both layers:

  acquisition/linking and loaded-import validation.
Fixing the source closure alone cannot make the lifecycle accept GDI.

Fixed builtins are classified by src/08c-ne-loader.wat:
win16_system_module_id; USER/GDI/WIN87EM already have real dispatcher paths.
CARDS has a fixed id but still requires a real image (dll-loader.js). Thus
"every fixed id is fileless" would be an incorrect classification.

TOOLHELP requires additional ownership work. lib/dll-loader.js already calls
it emulated for standalone Win16 loads, but its identity uses a dynamic name
slot, not a fixed system id. win16_dynamic_module_id can allocate that slot
during relocation; blindly skipping TOOLHELP in bridge preflight would leave
the slot outside the bridge dependency/reference/rollback protocol. The
Win32 bridge needs an owned emulated dependency identity that remains valid
across two importers, unload/rollback, concurrent coordinators and slot reuse.
Do not manufacture a guest DLL or success-returning export to obtain it.

The current win16_toolhelp switch implements 54, 62, 67, 68, 72, 75, 76, 77,
but not 80. If WDIR62 calls 80 after correct admission it must still fail
loudly until real behavior is implemented. Static import presence does not
establish that the ordinal is called during initialization. No next runtime
blocker or successful initialization is claimed.

Required validation for a repair: source-only closure tests for fixed
fileless builtins versus real CARDS/custom/missing modules; real far-call
fixtures for USER/GDI/WIN87EM; TOOLHELP identity reuse with two importers,
rollback and final release; unknown builtin ordinals retain fail-fast;
unsupported dynamic dependencies remain diagnostic. Native tests/build and
another original run require a fresh root runtime grant.
