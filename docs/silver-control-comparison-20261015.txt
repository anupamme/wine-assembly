Capture and cleanup limits

Each session has a300s controller deadline,8MiB retained console budget,
28-screenshot cap and20s observation windows. The outer supervisor bounds
setup/hung cleanup at320s TERM/325s KILL, targeting only observed descendants
whose PID start time still matches. Normal exit closes browser/server and
rechecks source/media. Actual browser termination/PID absence remains untested
until runtime; inspect cleanup rather than assuming it worked. Do not run a
second browser if cleanup is unknown. Run outputs are self-contained except
historical config/source paths, which identify inputs rather than artifacts.
The supervisor records postflight but does not publish a dashboard result:
the reviewer must inspect images/logs, hash the final artifacts and write
result.json last using ops/README.md. Never mark gameplay from normal exit.

Remaining acceptance

The saved held-button field is host state, not proof that the guest consumed
input. No new guest input-poll tracing is implemented. If needed, use an
existing bounded diagnostic under a separate agreed comparison; do not turn
tracing into a silent clock/performance confound. The old readmes do not
specify the ground-click/selection contract, so failed clicks alone cannot
diagnose an input bug. Establish repeatable displacement of the hero relative
to fixed scenery that follows ordinary input and differs from the idle
control. Compare actual reviewed captures and retain full source/input/backend
identity. Runtime setup, scene readiness, matched-clock timing, cleanup,
actual control interpretation and player control all remain unverified here.
